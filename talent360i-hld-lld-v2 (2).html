System context

4

Five agents

An agent here means something with control flow of its own — it loops on its own judgement, or it pauses for a human and resumes. A single prompt with a single response is a service call, and calling it an agent invites a question you do not want asked.

Why five and not two

Each of the five has a loop with a stopping condition, or a pause for a human, or both. Blueprint composition is a real optimisation — selecting from 38 competencies against grade-specific targets under a fixed item budget, with a coverage constraint that can fail. Descriptive answers are a first-class question type needing rubric scoring and escalation. Development plans draw from a training catalogue and curated SOP links, and a plan leaving a critical gap unaddressed is rejected and recomposed. Five is defensible; six would not be, which is why insight narration stays a service call.

5

Architecture

On deployment. An embedded store is not incompatible with running on a server — what breaks it is separating the process from its file, as with serverless functions or an ephemeral container filesystem. One container with a persistent volume on any existing project VM works. If Postgres happens to be available on that box, it is a one-line configuration change and worth taking, but it must not block Sprint 1.

The iteration rule that matters most

Tuning a prompt on five items costs about 8,500 tokens per cycle, so the iteration budget buys roughly twelve cycles a day. Tuning on fifty items costs 85,000 and buys one. The learning is identical. Prove the prompt small, then run the batch once.

Enforcement

  • The budget guard checks the agent's remaining cap before dispatch, not after
  • At 80% of an agent's cap the interface warns; at 100% that agent is blocked and the rest keep working
  • Cache hits are recorded with zero tokens, so restarting during development is free and the burn-down chart shows what caching saved
  • Demonstration day costs roughly 20,000 — one live generation and one evidence session, everything else warm from cache

Dual-framework model

The single most important schema decision. Get this wrong and the second function is a rewrite.

CREATE TABLE frameworks (
  framework_id   TEXT PRIMARY KEY,      -- 'finops' | 'rd'
  name           TEXT NOT NULL,
  level_count    INTEGER NOT NULL,      -- 6 | 3
  zero_means_unassessed BOOLEAN NOT NULL
);

CREATE TABLE framework_levels (
  framework_id   TEXT NOT NULL REFERENCES frameworks(framework_id),
  ordinal        INTEGER NOT NULL,      -- canonical order, 0..n
  code           TEXT NOT NULL,         -- 'L3'      | 'moderate'
  label          TEXT NOT NULL,         -- 'Level 3' | 'Moderate'
  descriptor     TEXT NOT NULL,         -- behaviour at this level
  evidence_note  TEXT,                  -- what evidence looks like here
  design_note    TEXT,                  -- what an item at this level validates
  PRIMARY KEY (framework_id, ordinal)
);

CREATE TABLE competencies (
  competency_id  TEXT PRIMARY KEY,
  framework_id   TEXT NOT NULL REFERENCES frameworks(framework_id),
  name           TEXT NOT NULL,
  definition     TEXT NOT NULL,
  comp_type      TEXT NOT NULL,   -- 'admin' | 'process' | 'behaviour'
  assess_method  TEXT NOT NULL,   -- derived: 'question' | 'evidence'
  sop_links      TEXT             -- json array of curated references
);

CREATE TABLE role_competency_targets (
  role_id        TEXT NOT NULL,
  competency_id  TEXT NOT NULL REFERENCES competencies(competency_id),
  target_ordinal INTEGER NOT NULL,
  is_critical    BOOLEAN NOT NULL DEFAULT 0,
  PRIMARY KEY (role_id, competency_id)
);

Everything downstream — levels, gaps, distribution, movement — reasons over ordinal. Every screen renders label. A leader looking at RD sees Beginner, Moderate and Expert; a leader looking at FinOps sees L0 to L5; the level engine is identical for both.

Do not normalise the two scales onto each other. Mapping Moderate to L3 invents a precision nobody agreed to, and the first SME who notices will be right to object. Compare within a framework; across frameworks, compare only gap-to-target as a percentage, and label it as such.

Agent specifications

A3 and A5 follow the same shape with a single verification loop and no human pause: A3 escalates a borderline score to the SME queue rather than pausing the graph, and A5 recomposes once if a plan leaves a critical gap unaddressed.

A1 · Blueprint agent

class BlueprintState(TypedDict):
    role_id: str
    grade: str                      # B2 | B3 | B4
    framework_id: str
    candidate_competencies: list    # from role_competency_targets
    question_budget: int            # total items for this assessment
    allocation: dict                # competency_id -> item count
    routed_to_evidence: list        # behaviour competencies
    coverage_gaps: list
    passes: int                     # ceiling of 2

nodes:
  select      -> filter by grade target (17 / 31 / 38)
  route       -> comp_type 'behaviour' → evidence; else → questions
  allocate    -> distribute item budget, weighting critical competencies
  verify      -> every non-behaviour competency has >= min_items;
                 critical ones have >= critical_min
  rebalance   -> only if verify fails, at most twice

The loop is the allocation constraint: a fixed item budget across 31 competencies with critical ones needing more depth. verify is deterministic Python, so only allocate and rebalance cost tokens.

A2 · Question agent

Unchanged from v1 in shape — ingest, generate, self-check, one regeneration, persist, pause for the SME, apply decisions, schedule gate — with two additions. Generation context now includes the SOP clause the competency references, and the self-check adds a fifth criterion: does the item test the SOP clause it cites? Grounded items are markedly easier for an SME to approve, because approval becomes verification rather than judgement.

A3 · Assessment agent

nodes:
  parse     -> extract claims from the free-text answer
  score     -> against the level descriptor and rubric, with citations
  confidence-> agreement between rubric dimensions
  route     -> confident → record
               borderline → SME queue, flagged, with both readings

Multiple-choice scoring never reaches this agent — it is arithmetic.

A4 · Evidence agent

Handles the six behavioural competencies. Elicit from the level descriptor, assess sufficiency, probe at most three times, summarise with the associate's own words quoted and the missing element named. It produces an evaluation and never a decision; the manager gate follows. Injection controls apply here in full, since this is the only place free-form user text reaches a model.

A5 · Development plan agent

nodes:
  gather   -> confirmed gaps for the person, ordered by severity
              and criticality
  retrieve -> candidate training from the catalogue + curated SOP links
  compose  -> sequenced plan; each step names the descriptor clause
              it closes
  verify   -> is every gap addressed? is the sequence feasible?
  revise   -> once, if verify fails

The verification step is what makes this an agent rather than a lookup: a plan that leaves a critical gap unaddressed is rejected and recomposed.

Routing rules

The supervisor is deterministic. It routes on competency type and stage, and it costs no tokens.

def route(competency, stage) -> Agent:
    if stage == "design":
        return A1

    if competency.comp_type == "behaviour":
        # 6 of 38 in RD — no multiple-choice item can certify these
        return A4 if stage == "assess" else A5

    if stage == "author":
        return A2
    if stage == "assess":
        return A3 if question.type == "descriptive" else DETERMINISTIC
    if stage == "plan":
        return A5

Live versus pre-seeded — say this out loud

Three things run live: A1 blueprint composition, A2 generation with self-check, and A4 evidence. Everything else reads from a database seeded with the organiser data plus three months of backdated history so distribution and movement have shape.

Declare that in one sentence at the start. Judges assume seeding anyway; volunteering it buys credibility, and it removes the risk of being caught mid-demo pretending otherwise.

The beat that decides the demo

2:15 — the self-check failing an item and regenerating it. Every team will show questions being generated. Very few will show the agent rejecting its own output before a human is involved, which is the one moment that distinguishes an agent from a prompt. Rehearse that transition until it is smooth, and give it a beat of silence before speaking.

Rehearsal plan

  • 19 Sep, morning — two dry runs, no audience, fix what breaks
  • 19 Sep, midday — record the walkthrough while everything is fresh
  • 19 Sep, afternoon — two timed runs with someone unfamiliar watching, and let them interrupt with questions
  • 20 Sep, morning — two final runs, then stop. Do not touch the code.

Six runs total. The target is not perfection; it is that the driver stops needing to think about where anything is.

Pre-flight and failure playbook

Twenty minutes before

  • Database reset to the seeded snapshot — a demo run leaves state behind, and the second run of the day will not work otherwise
  • DEMO_MODE on; cache warmed by running the whole path once
  • Remaining token budget checked and screenshotted
  • Endpoint reachability confirmed with one cheap call
  • Browser tabs pre-opened at each starting screen, in demo order
  • Zoom at 125%, notifications silenced, second monitor mirrored not extended
  • Backup recording on a phone, not only on the laptop
  • Printed run sheet in front of the driver

When something breaks

FailureDo thisSay this
Endpoint slow or rate limitedCached path serves the rehearsed response. Keep going.Nothing. Do not narrate infrastructure.
Endpoint down entirelySwitch to the recording at the current beat and continue narrating over it.“We’re on the recording from here — the shared endpoint is having a moment.”
A generated item looks weakDo not hide it. Reject it in the SME queue with a real reason.“That one is not good enough, and this is exactly why the gate exists.”

Questions to have answers ready for

QuestionAnswer
How do you stop it hallucinating a wrong answer key?Three layers: generation is grounded on the indicator and the SOP clause, the agent self-checks four criteria and regenerates on failure, and an SME approves before anything is scheduled. Nothing unapproved reaches a candidate.
What stops manager confirmation becoming manager bias?The calibration panel — approval rate against peers, rejection rate with evidence attached versus without, and time to decide. Advisory to leaders, never an automatic override. This was your question in the orientation call.
Does the AI decide someone’s level?No. Levels are computed in code from stored responses and confirmed evidence. The agents produce proposals; two human gates stand between a proposal and a confirmed level.
What did this cost in tokens?Show the burn-down by agent. Roughly 300,000 for a full FinOps bank, generated once and reused. The demo itself cost about 20,000.
Would this work for a third function?A framework registry row plus the competency list. RD and FinOps use different level scales already and share one engine — that is the switch you saw at 6:00.
Is this using real employee data?No. Synthetic identities throughout, enforced by tests. The published dataset checks run as part of our suite and are green.
Could it be used for hiring?The proficiency profile supports it, but we did not build a hiring view because scope was set as upskilling. It is a roadmap item, not a gap.
How long to production?The agent layer and schema move as they are. Production needs managed identity, a hosted database, and platform dashboards — Dataverse and Power BI being the natural target given the Teams and Workday alignment.
Why five agents rather than one prompt?Each has control flow of its own — a loop with a stopping condition, or a pause for a human. Anything that was a single call stayed a service call.
